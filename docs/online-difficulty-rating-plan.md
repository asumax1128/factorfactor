# EASY / NORMALランダム対戦：移行・認可・実装案（承認前）

基準：`42011a6`のオンライン実装。今回mainに反映した`9fa9ac3`は数学の塔のみの製品変更で、オンラインの関数・Firebaseルール・既存レートは変更していない。この文書と監査テストは設計ブランチに置き、本番クライアントへ新マッチングを組み込まない。

## 調査の根拠と限界

コード、ユーザー提供の最新Consoleルール保存ファイル、初回統合ルール候補の`accounts`・`rooms`・`qm`を比較した。この3枝は同じ。実エミュレータで合成アカウントを用いて認可を検証した。

本番データの管理用接続はこの環境に設定されていない。本番アカウント一覧、実レート、残存する部屋の件数、別途保管された対戦ログ、現在の課金プラン、現在配信中のルール全文は直接取得していない。以下のデータ構造はコードが読み書きする構造と提供ルールからの確認であり、本番全レコードの棚卸し済みとは主張しない。本番適用前に最新Consoleルールとの再比較と、管理者によるバックアップ・匿名化された集計情報の確認が必要。

## 1. 現在の保存・対戦・表示

| 用途 | パス／コード | 現在の動作 |
| --- | --- | --- |
| アカウント | `games/factor/accounts/$accountKey` | name、stats、prof、mis。アカウント連携は`logins/$accountKey/$anonymousUid`。 |
| レート | `accounts/$key/stats`、`ratingOf`、`recordMatch` | rating、season、seasonMax、maxRating、seasonHist。難易度別のレートはない。 |
| 勝敗 | 同stats | games、w/l/d、A/B/C別の勝敗、vs（相手別）、連勝、経験値、称号用集計。難易度別対戦履歴ではない。 |
| 待ち枠 | `games/factor/qm/slot` | 全難易度で1つの枠。25秒で古い枠扱い、8秒ハートビート。 |
| 試合 | `rooms/$4digitCode/meta,players,state` | stateにmode・diff・gid・seed・参加者・開始時レート等。ランダム対戦も通常部屋を使用。 |
| 投票 | `players/$uid/vote`、`startQmVote` | `vid:A-easy`など。方式一致なら採用、割れたらランダム。全員NORMALのときのみNORMAL。他はEASY。時間切れは方式ランダム。 |
| 結果 | `rooms/$code/result/$gid` | クライアントのwriteResultがtransactionで初回登録する。次戦開始時にresult等をremoveする。 |
| 順位 | BattleHomeのrank読込 | accounts全体からgames≥3を抽出、現在レート→勝率で並べ上位10件。画面を開いたときの取得で、継続購読ではない。 |
| 称号 | BADGES、badgesOf | statsから都度計算。既存ゴールド1580「ゴールドの風格」、マスター1820「頂点に立つ者」等。 |

Eloは初期1500、K=32、期待勝率は`1/(1+10^((相手R−自分R)/400))`。最初の10戦のマイナス変動は半分、ハンデありの変動も半分。毎月のシーズン切替で1500を超えた差分を半減し、1500以下は1500から開始する。既存の部屋対戦・大会・ランダムCPU/ゴースト代役は共通statsを使用している。CPU練習とは扱いが異なる。

対戦中の退出は8秒で脱落扱いとなり、残った側が勝つ処理がある。Aの同点は引き分け。投票中に2人未満になると決定処理が止まるが、退出時のサーバーによる失効処理はない。新方式では対戦開始前の取消と、開始後の退出による敗北を明確に区別する。

## 2. 認可・二重登録の問題

エミュレータで次を再現した。すべて合成データで、本番操作ではない。

- アカウント連携のないUIDからstatsへの書き込みは拒否される。一方、連携済み本人はrating=9000、games=999等を直接書ける。statsには計算式・有効試合の存在を検証する条件がない。
- 本人がstatsの下に新しいratingsV2を作ることもできる。そこに`.write:false`を追加しても親statsの許可が優先され、本人の書き込みを拒否できない。
- 部屋参加者はresultの空いているgidへ、試合との整合性が確認されていない勝敗を作れる。非ホストによる再書き込みは拒否されても、ホストには親階層の書き込み許可があるため上書きできる。
- UIの`recorded.current`は1回のマウントで二重記録を防ぐが、`recordMatch`自体にはmatchIdによる重複排除がない。同じinfoを2回呼ぶコードテストで2戦・レート+32となった。再接続・複数クライアントでも保証される仕組みではない。

したがって、既存recordMatchに`diff`を足してstatsに2レートを保存するだけの実装は採用しない。ホストのresultやクライアントのdrをそのまま信頼した新レートも採用しない。RTDBルールだけで既存の指数を含むElo計算と試合の正当性を完全検証する案にはしない。

## 3. 推奨するデータ構造とサーバー処理

新しい兄弟枝`games/factor/onlineRatedV2`を作る。既存stats・rooms・qmの書き込み許可を継承しない。新レート、確定結果、称号、ランキングのクライアント書き込みは拒否する。先生権限で直接レート変更を許すルールも設けない。更新するのは信頼されたバックエンドだけ。

```text
onlineRatedV2/
  config                       # 有効化・最小protocolVersion・移行番号
  queue/v2/{easy|normal}/...    # バックエンドが管理する期限付き待ち枠
  matches/$matchId/...          # 参加者向けの試合情報・確定結果
  matchPrivate/$matchId/...     # 検証用データ。クライアントには読ませない
  ratings/{easy|normal}/
    players/$accountKey        # rating, games, w/l/d, season, seasonMax, maxRating
    settlements/$matchId       # 両者の加減算済み台帳
  leaderboardViews/{easy|normal}/...
  badges/$accountKey/...
  legacyArchive/$migrationId/$accountKey
```

上位枝で包括的なread/writeを許可しない。自分の新成績はUID/accountKey連携確認後に読める。対戦情報はその試合の参加者だけ、ランキング用の名前・レート等の公開ビューは既存の方針に合わせて認証済みユーザーへ公開する。台帳・移行バックアップ・検証用情報はクライアント非公開とする。

待ち枠の作成・取得・取消・投票・対戦開始・結果確定はバックエンドがIDトークンを検証する。匿名UIDが有効でも、ランキング用accountKeyとのlogins連携を別途確認する。リクエスト中のaccountKeyだけで本人と判断しない。パスワード/PINはAPIやチャットへ送らない。

### マッチングと旧クライアント

1. 「すぐ遊ぶ」からEASY/NORMALを選択。選択したdifficultyとprotocolVersionをサーバーで固定した待ち枠を作る。
2. 同じ難易度・対応プロトコル・別アカウント・接続中の2人だけを原子的に組み合わせる。自己対戦や同一アカウントの二重待機を拒否する。
3. マッチ後はA/Bだけ投票。両者一致は採用、同票・未投票/時間切れは既存どおり方式をランダムに決める。difficultyは投票やホスト更新で変えられない。
4. 待機中の取消・再検索・失効・通信断はサーバーの期限付きticketで処理する。取消とマッチ成立が競合した場合は、確定した状態を返し、古い取消で相手の新ticketを消さない。
5. 投票中に退出した場合は開始前の無効試合とし、レートは変えない。開始済みの対戦は既存の8秒退出判定・引き分け・勝敗をサーバー側へ移し、同じ既存ルールになることをテストする。
6. 新対戦は既存`qm/slot`と4桁roomsから分離。新クライアントは新キューが使えなくても旧ランダム対戦へ黙ってフォールバックしない。更新案内またはエラー/再試行を表示する。旧クライアントには新matchを渡さず、新レートの書き込みも認可で拒否する。
7. 部屋番号による対戦、大会、レイド、CPU練習の既存経路は維持する。旧ランダム対戦をいつ停止/案内するかは別途承認し、進行中の旧試合を切断しない。

### 信頼できる結果とレート更新

サーバーが発行した試合・参加者・難易度・方式・問題に対する因数選択を検証し、既存の因数分解エンジンと勝敗計算を再利用して結果を決める。ホストの任意result、自己申告レート差分、自己申告HP/勝利だけでは確定しない。特にB方式の攻撃・HP・時間経過も検証可能な状態として扱う必要がある。サーバー側の検証を省いたクライアント試作は、本番の安全なレーティング実装と区別する。

1試合のmatchIdと難易度をサーバーで確定し、該当難易度のratings枝のtransactionで**両者のレート・戦績とsettlements台帳を同時に**更新する。台帳があれば再処理せず同じ結果を返す。片方だけ更新したところで障害になる構成にしない。transaction内部に副作用を置かない。

表示用ランキングは確定台帳/成績から作る派生ビュー。非同期反映の世代番号を表示用データへ持たせ、古い処理が新ランキングを上書きしない。確定結果と順位反映中を区別する。称号も確定済み成績からのみ発行し、配信の再試行は冪等にする。

Elo、初期値、ハンデ補正、シーズンの既存式は原則維持。最初の10戦の救済は各難易度の新対戦数を基準にする案。試合の開始/終了が月をまたぐケース、同時対戦の禁止・期限、無効試合の台帳化もテストで仕様を固定してから公開する。

### CPU・ゲストの範囲（承認事項）

推奨案：新しいレーティング対象は、連携済み別アカウント2人のランダム対戦A/B。部屋番号対戦、大会、ゲスト対戦、CPU・ゴースト代役は新レートに加算しない。これらの既存ゲームや旧記録は残す。CPU代役を使う場合は「練習・レート対象外」と明示し、待機中に同じ難易度で練習できる導線を維持する。

現行はランダムCPU/ゴーストでも旧レートが動くので、この除外は今回の調査からの**提案**であり未決定。新レートにもCPUを含める場合は、サーバーが管理するCPU対戦と評価方針を別途設計・承認する必要がある。

## 4. 安全な移行案

**推奨：旧総合を履歴として保持し、EASY/NORMALを各1500から開始する。**

既存statsは削除・リセット・上書きしない。新対戦は新しい成績を使う。旧statsのrating/season/seasonMax/maxRating/seasonHistと旧称号の獲得状況を、移行番号・取得日時付きの旧総合履歴として保管する。元データは自己申告を許していた記録なので、履歴を新方式で検証済みの成績と誤表示しない。

過去の正確な再計算に必要な、全試合の難易度・確定日時・双方の開始レート・結果・補正・一意ID・順序はコード上で永続保存していない。vsやA/B別勝敗、学習記録、ghostlogだけでは復元できない。roomsは次戦で状態を入れ替え、結果を削除するので残った一部からの再計算もしない。別途完全な信頼できる外部履歴がある場合だけ再調査する。

承認後の移行手順：

1. 最新ルールと現在の構造を管理者の画面/安全な接続で確認。実名・PIN・秘密鍵をチャットへ送らない。まずstatsのフィールド一覧、件数、難易度付き全対戦履歴が存在するかを匿名化して確認する。
2. 対象範囲のバックアップを管理者が取得し、所有者の暗号化した保存先2か所へ保管。公開GitHubやPagesへ実データを入れない。復旧テスト・ハッシュを記録する。
3. 合成データでdry-runし、旧statsの差分がゼロ、新2レートが1500、旧称号保持、移行の再実行で同じ結果になることを確認する。
4. 新サーバー・新枝のルールだけを先に準備。現行accounts/rooms/qmを不用意に変更しない。新機能の有効化フラグはOFF。
5. 新枝へ移行番号をキーに冪等な初期化を実施。既存新レートがあれば上書きしない。ユーザーが増えた場合も初回利用時にサーバーで同じ1500初期化を行えるようにする。
6. 先生/限定テスターで実Auth・新サーバー・旧クライアント混在・端末競合を検証した後、新クライアントと機能フラグを整合させて公開する。
7. ロールバックは新キュー受付を停止してUIを戻す。確定済み新レート・台帳・旧履歴は保存し、旧statsへ加算し戻さない。進行中試合の扱いも手順に含める。

旧クライアントが旧statsへ書く間は元の総合値が変わり得る。移行時点の旧総合履歴はスナップショットとして固定し、ライブの旧statsと区別する。旧総合ランキングを履歴表示にする範囲・旧クライアント終了日は承認前に決める。既存称号は改名せず、移行時点で獲得済みのIDを保存して、新機能の導入で消えないようにする。

## 5. ランキングと称号の提案

EASY/NORMALの2タブ。自分の各レートと対戦数は常時確認でき、未対戦は「1500・未対戦」。掲載基準は既存の3戦以上を各難易度に適用する案。未対戦/1〜2戦は自己成績には表示するが順位一覧には載せない。

各難易度の確定rating→勝率→同率時accountKeyの順で安定ソートし、同一レート・勝率には同順位を表示する案。既存どおり上位10件＋自分の順位。該当難易度の結果だけがそのランキングを更新する。履歴の旧総合、ソロなど他ランキングは別経路のまま維持する。

称号はまず5個だけ追加する案。既存名称・獲得条件は変更しない。

| 新しい称号 | 提案条件（新方式で確定済みの生涯最高値） |
| --- | --- |
| EASYの達人 | EASYで1730以上（既存ダイヤ帯） |
| NORMALの達人 | NORMALで1730以上 |
| EASYマスター | EASYで1820以上（既存マスター帯） |
| NORMALマスター | NORMALで1820以上 |
| 双璧のマスター | 両難易度でそれぞれ1820以上 |

各難易度で少なくとも1回の有効対戦があり、新サーバーが確認した最高値だけを使う。旧総合maxRatingや片方の条件からもう片方を獲得させない。月次リセットで既得称号を取り消さない。名称・5個という数・閾値は**未承認の提案**。

## 6. 必須テストと公開条件

実装前の調査として実行済み：`online-rating-audit.cjs`の旧recordMatch重複再現、現行ルールの本人/他人、自己申告レート・子階層の許可継承、結果作成/ホスト上書き、独立サーバー枝への書込拒否。通常のオンライン/大会/レイド/アカウント/ランキング回帰も通過。

新仕様のEASY/NORMALマッチング・レート更新・ランキング・称号は**未実装・未検証**。数学の塔のテスト成功をこの新仕様の検証成功と扱わない。

承認後に実装するテスト：

- EASY同士/NORMAL同士だけ、混在拒否、同一accountKey/古いprotocol拒否、旧4桁部屋との完全分離。
- A/B一致・割れ・時間切れ、difficulty変更拒否、投票中退出、キャンセルと成立の競合、再検索・期限・復帰。
- サーバーの問題判定とA/B勝敗、8秒退出・引き分け・無効試合、クライアントによるdr/rating/winner偽装拒否。
- 選択難易度だけ更新、EASY1800/NORMAL1500の成立、両者の原子的更新、重複確定・再送・通信断後の再試行。
- 0/2/3戦の順位掲載、同率順序、自分の両レート、世代の古いランキング反映拒否、サーバー成績との一致。
- 片側のみの称号・両側マスター・月次リセット後の保持、旧称号保持。
- 移行再実行・一部障害・旧データ不変・バックアップ復旧、新受付停止ロールバック。
- 本番の実Auth/UID連携、PC/iPhone Safari、通信遅延時の対戦テンポと結果反映。全既存モード・塔セーブ・音声の回帰。

## 7. 次に必要な承認・設定

1. 旧総合履歴保持＋新2種類1500開始、ランキング各3戦以上、旧総合表示の切替時点。
2. 新レートの対象を人間2人のランダムA/Bとする範囲。CPU/ゴースト・ゲスト・部屋対戦・大会の除外は要確認。
3. 上記5称号の名称と1730/1820条件。
4. 信頼されたバックエンドの配置先・料金・権限・新Firebaseルール/新枝の追加・移行実行。

リポジトリには現在サーバー実装がなく、この環境にも管理用GCP接続はない。Firebase Cloud Functionsを利用する案が既存Auth/RTDBとの連携上は自然だが、一般にBlazeへの設定が必要で、無料枠があっても費用発生の可能性がある。現在のプランと利用できる既存バックエンドを確認し、費用・予算通知・運用権限を提示してから承認を求める。課金サービスを今回追加・有効化していない。ブラウザだけで代替して安全なサーバー実装と称することもしない。
