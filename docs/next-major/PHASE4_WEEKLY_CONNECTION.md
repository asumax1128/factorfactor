# 第4次：週間ボスの開発限定接続

本番の完成・有効化ではない。`WeeklyRaidApp`と実際の`RaidPlay`を候補APIへ接続した。起動条件は**ブラウザーがloopback、DB参照先もloopback、projectIdがdemo-factorfactor-tower**の全成立。URLパラメーターだけでは有効にならない。登録アカウントのみ。通常の本番／ゲスト経路の条件は変更しない。

## 保存と処理

- 既存の問題生成と正答ペアを検証してから`reserve`。成功後に実ゲームを開始する。
- 5枠・サーバーJST日付・元予約の`resume`は既存候補APIを利用。
- `weeklyNextV1/games/<account>/runs/<id>`へ単調な連番と累積ダメージ／応援／宝箱等をcheckpointする。同じ連番・同じ内容は再送として扱い、内容不一致は拒否する。Firebaseがオブジェクトのキー順を変えたり空配列を省略したりしても同じ値と判断する。
- 開発画面のHPは既存`weeklyInfo`へ開発ダメージを重ねて計算する。ボス個性・怒り・弱点・気まぐれルール・ダメージ式は変更しない。他ユーザーの開発領域は読まず、この画面の開発アカウント分だけの検証用表示。
- 終了時はserver timestampでセッション時間（延長を含む）経過を確認。settlingへ固定→予約のfinish→報酬とreceiptを同じ開発アカウントtransactionで確定する。EXP式は従来の出撃式を維持し、初日倍増は予約のJST開始日を使用。再送時は確定済み報酬を返すだけ。
- 途中退出はabandoned、予約返還なし、完走receipt／完走EXPなし。途中までの開発ダメージは残る。切断は返還せず、同じ予約IDで復帰する。
- 開発中は旧`accounts/.../stats`、`raidw/.../dmg`、`sup`、`kill`、学習報酬へ書き込まない。報酬を模擬する専用statsへだけ保存する。したがって旧討伐・週間締め・とどめ報酬の新API統合まで完成した意味ではない。

## 検証

- 実SDK Auth/RTDB Emulator：初期検証失敗で予約0、2端末resume、同一checkpoint再送、改変競合拒否、時間前finish拒否、同時finishの報酬一度だけ、再復帰、途中退出、同時予約を含む合計5回上限、他人アクセス拒否、旧データパス不変。
- 実React＋モック通信：375／390／430／1440pxで出撃→実ドラッグ→ダメージ→再読み込み→同じ予約へ復帰→時間経過→receipt／EXP、元戦績・レート・装備不変。
- 既存204関数のAST比較とソロ／学び／CPU／週間ボス／デイリー回帰成功。`weekly-legacy-projection.cjs`は開発専用分岐を除いた従来の開始／戦闘／終了／報酬コードを元コードと比較する。関数全体の除外はしない。
- 開発中の失敗：Firebaseのキー順差で同じcheckpointが不一致になったため、RTDBの空値省略も考慮した正規比較に修正。ブラウザテストは既存aria-labelと週の90秒ルールに合わせた待機へ修正。待機時間の延長やテスト無効化なし。

## 残る制約（公開前に必須）

1. 復帰ではダメージ／時刻／予約／報酬を復元するが、解いていた盤面・コンボ・途中の反撃状態を完全保存していない。全戦闘状態の厳密な復帰は未完了。
2. 予約確定後かつrun保存前の通信断について、予約の再発見と開始再試行UIが必要。自動返還はしない。
3. 開発領域のルールは本人のsandboxへのアクセス境界であり、クライアントによる戦闘結果改ざんを証明・拒否する完成済み競技サーバーではない。旧の実データへ接続しないこと。完成receiptと全報酬の認可・不変性・復旧outboxの追加設計が必要。
4. ホーム／全参加者を含む共通HPと専用開発投影の統合は未完了。HP90,000の適用週は未承認のまま、旧meta／HPは変更しない。
5. ゲストは現行経路のまま。候補5回制へ無断で移さない。匿名認証UID単位だと端末変更で回数が分かれるため、アカウントキー相当の継続識別の承認が必要。

候補ルールを本番へ公開しない。正式本番接続には既存認可を含む再レビューと所有者承認が必要。実機Safari／Chromebookは未検証。

## 追加：予約直後／報酬確定途中の障害復旧

- reserveに任意のweek／durationメタデータを追加。従来のメタデータなし予約形式もAPI・ルールで維持し、新規メタデータは後から差し替え不可。
- 出撃予約がコミットした時点で、次のrun保存を待たず復帰tokenを保存する。run作成前に切断しても、初期盤面の再検証→元予約resume→同じstartAt／durationでrunを作れる。新しい枠や開始時間を作り直さない。
- 開始処理の同ID再送は既存runを先に確認。UI再試行も保存済みtokenを使い、別IDの新規予約へ流さない。古い週のtokenは現在週の出撃として流用せず、旧予約は保存したまま案内する。
- finish receipt作成後かつ報酬transaction前の中断ではrunがsettlingとなる。復帰後に新しいcheckpointを書こうとして失敗する問題を修正し、保存済み内容でfinish／報酬処理を冪等に再開する。
- SDKと実UIへの障害注入で両方を検証した。元の5回制・JST日付・旧APIの許可／拒否テストも成功。

上の「残る制約2」のうち、新メタデータ付き予約のrun作成前障害は解消した。古いメタデータなし予約から週／制限時間を推測復元しない。解答中の盤面／コンボ／ボスギミックの厳密復帰、全報酬・全員HP統合等は引き続き未完了。
