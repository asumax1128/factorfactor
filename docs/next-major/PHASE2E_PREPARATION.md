# Phase 2E：週間ボス制限の候補API（アプリ未接続）

現行ゲームにはまだ接続しない。本番ルール／週途中データ／既存meta／ダメージ／報酬は変更しない。HP3倍や1日5回が現行画面で有効になったという意味ではない。

## 開発済みの独立部分

- `src/weekly-next.cjs`：新しい週を作る時の基本HP選択。従来30,000、新規で承認済み開始週以降90,000。既存metaは旧30,000を保持し、新ポリシーで作られたmetaの基準値は凍結する。Monday/JSTの境界をテスト。実際の適用週はnull相当の未指定で、アプリはこのAPIを呼ばない。個体倍率・怒り補正を変更するコードは追加しない。
- 候補パス`games/factor/weeklyNextV1/attempts/<account>/<JST日>/slots/0..4`。出撃予約と`finish`完走報告を分離。サーバーtimestampから日付を読み、ルール側nowで日付と時刻を検証。
- 同一アカウントの同一端末内の予約は直列化し、端末間はRTDB transactionで排他化。新規IDは最大5つ、同ID再送は同じ予約。予約は削除不可で、退出／切断による返還はない。resumeは元の開始日を参照し、日付跨ぎで再消費しない。
- 完走報告は開始IDに結び付け、同じ予約への同時報告・再送は不変の同一レコード。未完走は受け付けない。これはクライアント報告であり、全問／戦闘の正当性をサーバーで検証した証明ではない。報酬／称号／累積完走回数へまだ接続しない。
- `firebase/next-weekly.fragment.rules.json`は新サブツリーだけの候補。単独公開するファイルではない。既存全体ルールにメモリ内で合成してEmulator検証。祖先に広いwrite許可がないことをテストで確認。本人のログイン権限、5枠・ID重複拒否、旧枠の不変、時計改変拒否、他人の読み書き拒否を検証する。既存ルールの公開・緩和はしていない。

## 実SDK検証

`tests/weekly-next-emulator.cjs`：2認証端末から6件同時予約し、5件だけ成功。満枠で同ID再送、別端末resume、同時完走報告の冪等性、予約／完走削除・6枠目・他人取得／書込・偽時計・未来日付を拒否。成功。既存Auth/RTDB Emulatorとdemoプロジェクトだけを使用。

開発時に2点を検出・修正：同一SDK内の並列transactionがローカル未確定値をまとめて送るため既存日次APIと同じ直列化を適用。timestampのローカル推定値を返さず、確定後のgetでサーバー記録を返す。権限ルールを緩めて解決していない。

## 未完了と次の接続手順

1. 適用する開始週の承認を受け、HPポリシーを管理者だけが固定できるルールと新週meta初期化を追加検証する。この候補APIだけでHPポリシーの改変防止が完成したとは扱わない。
2. 現行WeeklyRaidAppの開始前検証・出撃予約・開始時刻・終了処理へ接続し、同一出撃IDによるダメージ／EXP／報酬の一度だけ処理を設計する。旧処理と二重更新しない。ホーム／戦闘／結果はweeklyInfoを共通利用する。
3. ゲストの制限適用と互換性を決める。現在の候補は登録アカウントのみで、既存のゲスト導線を勝手に廃止しない。
4. フレンドレイドの公式10戦は、旧statsと移行済みE/Nを単純合算しない。どの旧記録を公式人間戦として証明できるかの照合が未完了で、開催ゲートはまだ実装しない。
5. 4難易度UI／設定分離と鬼の数値は未実装・数値未承認。クラスレイドとRAID_POWERを共有する現状を維持し、未承認の鬼を有効化しない。

本番でのデータ移行・ルール公開・HP切替は別承認が必要。今回の候補ファイルをConsoleへコピーしないこと。
