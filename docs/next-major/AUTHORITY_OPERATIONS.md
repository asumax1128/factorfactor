# authority運用の境界と本番承認事項

2026-10-16。Emulatorの検証結果と、本番構成を混同しない。

|選択肢|Sparkとの関係|費用・運用上の制約|判断|
|---|---|---|---|
|現行GitHub Pages＋Realtime Databaseだけ|静的配信／DBにはNode workerを常駐実行できない|ホスティング追加費用はないが、このauthorityを実行する環境がない|正式報酬の証明をブラウザへ戻す代替は採用しない|
|所有者管理の既存サーバーでNode worker|DBをSparkのまま使う構成は技術的に可能|既存機器なら追加ホスト料金0円の場合もあるが、電源・回線・監視・秘密鍵保管・バックアップが必要。新規ホスト料金は事業者未選定のため未確定|常時稼働可能な管理環境がある場合の候補。資格情報はブラウザ／Gitへ入れない|
|Cloud Functions／Cloud Run等の管理バックエンド|課金アカウント・対象サービスの利用条件確認が必要。Firebase Functionsの本番利用にはBlazeが必要|実行時間・CPU／メモリ・最低インスタンス・リージョン・DB通信量で変動。現時点で測定値とホスト選定がなく、月額の確定見積もりはできない。無料枠だけで0円保証はしない|運用は容易になるが、有料化と構成変更の明示承認が必要|

参考（価格・条件は採用時点で再確認）：[Firebase料金](https://firebase.google.com/pricing)、[Cloud Run料金](https://cloud.google.com/run/pricing)。今回これらのサービスの作成・デプロイ・プラン変更は行っていない。

## 最小構成の提案（未承認）

信頼できるバックエンド1系統で、認可済み入力を検証し、状態・確定イベント・報酬receiptを原子的に保存する。二重起動時もDB transactionにより同じ要求の重複適用を拒否する。停止時は入力を確定ACKせず、クライアントは同じrequest IDで再送する。再起動は管理側保存状態・確定ログから継続する。

現在の週間Emulator実装は一週間全体をtransactionに載せるため、そのまま本番運用可能とは扱わない。250ms周期ならworker1台だけでも最大4回/秒、2台なら8回/秒の全体処理になる。人数・履歴増加時の転送量評価と、イベント駆動／履歴分割が本番設計の残課題。Sparkの許容量内で使えるかは負荷と取得量を測定して判断する。

本番構成承認がなくても、Emulator実画面接続・認可・再起動試験は進める。本番構成未決定のまま「公開承認待ち」とはしない。
